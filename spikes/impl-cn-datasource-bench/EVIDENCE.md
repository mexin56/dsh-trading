# Spike 证据：中国 A 股公开行情源「时延 + 并发」现场实测（腾讯 vs 东方财富）

探针日期：2026-10-14（Asia/Shanghai 15:03-15:15，A 股收市后）。
取数穿过**实现**：`packages/connector-tencent/src/rest.ts` 与 `packages/connector-eastmoney/src/rest.ts`
的源码类，用 `./node_modules/.bin/tsx` 直跑 `.ts`（不用 `lib/` 构建产物，避免与并发 build 竞争）。
传输、计时、落盘由本目录 `transport.mts` 接管；连接器只负责 URL 拼装与解析。

## 请求预算与节流（对账）

| 源 | 脚本内计数 | 另计 | 实际合计 | 约定上限 |
|---|---|---|---|---|
| 腾讯 | 196 | +1（传输冒烟） | **197** | 200 |
| 东财 | 199 | +1（传输冒烟）+1（curl 独立客户端对照） | **201** | 200 |

- 东财**超上限 1 次（0.5%）**，用途是「同一时刻用 curl 做独立客户端对照」。触发原因见下：东财侧在本跑
  中途进入持续空响应状态，不做独立对照就无法区分「上游问题」与「本探针问题」。此处主动上报偏离。
- 节奏：同组相邻请求间隔 120ms；并发轮次之间 3000ms；覆盖抽样每项间隔 120ms。
- 头部策略：只发最小 `User-Agent: Mozilla/5.0` 与 `Accept` / `Accept-Encoding`（仓库 §7.1 口径）。
  **不发 Referer、不做浏览器伪装**——连接器传给 `fetch` 的 headers（含东财源码里那条 Referer）在替身
  fetch 里被丢弃，因此本探针发出的每个请求都符合上述口径。
- 只做只读取数：不下单、不写业务状态、不带任何密钥、不缓存也不再分发行情数据（`raw/` 内字节仅作证据）。

## 采样口径（Lead 2026-10-15 裁决 Option B）

- 时延 keep-alive：4 路径 × 20 次 = 80 次/源。**每组第一个样本就是建立连接的那次**（该组内后 19 次复用同一连接），
  故 keep-alive 表的 `DNS / TCP / TLS` 三列只有 1 个样本（即首个样本），`连接 p50` 因其余 19 次记 0 而恒为 0；
  另附「去掉首个样本」的稳态视图。
- 时延冷启动：`agent: false`，每次请求新建 TCP+TLS。每源只测 2 个代表路径（腾讯 `qt.gtimg.cn` + `web.ifzq.gtimg.cn`；
  东财 `push2.eastmoney.com` + `push2his.eastmoney.com`），各 20 次 = 40 次/源。
- 并发：固定在「单标的报价 600519.SH」路径，1 / 4 / 8 / 16 在飞各一轮、每轮 16 次请求。
  **c=1 轮直接复用 keep-alive P1 的 20 个样本——是同一批样本，不是独立的第二组**（脚本里就是同一份数据）。
- 分位：最近秩（nearest-rank）。失败样本计入分母，成功率按 `成功/样本` 单列，不静默丢弃。
- 时间字段：`dnsMs` = 请求开始→socket `lookup`；`tcpMs` = lookup→`connect`；`tlsMs` = connect→`secureConnect`；
  `connMs` = 请求开始→连接可用（复用记 0）；`serverMs` = 连接可用→响应头（TTFB 的服务端段）；`ttfbMs` = 请求开始→响应头。

## 结论（只写证据支持的部分）

1. **单标的报价在两者之间没有量级差**：keep-alive 稳态 p50 腾讯 41.7 ms / 东财 40.5 ms（p95 42.7 / 45.4）。
   冷启动 p50 腾讯 164.8 ms / 东财 153.4 ms。差异都在 2-12 ms 量级。
2. **连接建立是主导项**：冷启动比 keep-alive 稳态多——腾讯 P1 +123.1 ms（41.7→164.8）、P3 +138.0 ms（58.9→196.9）；
   东财 P1 +112.9 ms（40.5→153.4）、P3 +97.0 ms（50.0→147.0）。拆开看，冷启动组里 TLS 握手 p50
   腾讯 121.6 / 127.5 ms、东财 86.8 / 94.1 ms，TCP 连接 0.4-0.8 ms，DNS 1.6-2.4 ms。
   腾讯的 TLS 握手比东财慢约 33-35 ms。
3. **日 K 与分钟 K 的量级差来自路径**：日 K 100 根 keep-alive p50 腾讯 58.9 ms（8.9 KB）/ 东财 50.0 ms（7.2 KB）；
   分钟 K 腾讯 5m 71.7 ms（9.3 KB）/ 东财 1m 52.4 ms（87.6 KB，trends2 ndays=5 整窗）。
   东财 1m 用更大的下行体换到更低的 p50，但 p95 更高（89.6 ms）。
4. **腾讯在 1/4/8/16 在飞并发下没有降级**：全部 HTTP 200，无 429 / 无 5xx / 无连接重置；
   16 次请求的整轮墙钟随并发单调下降（c=1 1016.1 ms → c=4 304.1 → c=8 238.5 → c=16 195.9）。
   c=4/8/16 单请求 p50 高于 c=1，是一次性 TLS 建连摊在 16 次请求上的结果，不是被限流。
5. **东财在 c=4 即触发失效，且是「断」不是「慢」**：16/16 无 HTTP 响应；触发后对本机持续空响应 ≥9.5 分钟，
   且 curl 复现。**本次实测不支持「东财可以拿来跑并发」这个用法。**
6. **批量取数**：腾讯 `q=` 逗号列表全程 HTTP 200。同一批 8 只标的，一次请求 173.6 ms（1 次上游请求，含首次建连）
   对 N 次单请求 331.9 ms（8 次上游请求）。加长到 100 只仍 1 次请求 / 55.4 ms / 39.5 KB，
   但**只返回 87/100 行**——13 个未收录代码在响应里整行缺席，HTTP 仍 200、不报错、不降级。
   东财侧无数据（失效）。
7. **分钟 K 上限**：腾讯 `mkline` 在 `count <= 800` 时按请求返回（m1 800 根 / m5 800 根）；
   `count > 800` 时**静默降到 320 根**——HTTP 200、`code=0`、`msg=""`，没有任何错误提示；m1 与 m5 同形。
   产品代码 `Math.min(limit, 800)` 恰好把这个 320 悬崖挡在门外：产品路径发不出 >800 的 count，
   所以「超限静默降到 320」这个已知缺陷在本连接器的调用面上不可达。
   东财 1m 走 trends2：`ndays=5` → 1205 根 / 5 个交易日（约 241 根/日）；`ndays=10` → `rc=102` / 0 行。
8. **品种覆盖**：腾讯 8 项取到（含 ETF `159869.SZ`、指数 `000001.SH` / `000300.SH`、港股 `00700.HK`）。
   北交所 `835185.BJ` 在连接器层被拒（`normalizeCnSymbol` 的词汇只有 `sh|sz`，请求 0 次）；
   裸 wire `bj835185` / `bj832982` 有行，但都是 `87` 字段、行情时间 `20261014090000`（09:00:00）、成交量为 `0` 的占位形态。
   东财侧有直接证据的只有 `600519.SH` / `000001.SZ` / `300750.SZ` / `688981.SH`（见 `raw/eastmoney-P2-keep-alive.json`
   的 8 行响应）；其余 5 项因失效未取得。

## 推断（不是实测事实，已显式标注）

- **推断 1**：东财的空响应是本机在被 16 并发突发之后遭到上游限流/封禁，而不是端点整体下线——
  依据是失效紧随 c=4 突发之后、且同一时刻 curl 从本机取腾讯 226 ms 正常。
  **但本跑无法区分「针对本机 IP 的封禁」与「东财侧整体故障」**：远端路径探测未取得有效结果。
- **推断 2**：腾讯该报价端点对北交所只给占位行，而不是这两只票恰好都停牌——依据是两个不同代码
  （`835185` / `832982`）返回完全同形的 09:00:00 / 零成交量行。未做交易所公告核对。
- **推断 3**：腾讯 keep-alive 组里 DNS 从第一组的 11.5 ms 降到后续组的 1.5-4.4 ms，倾向于是
  本机/系统解析器缓存生效，而非上游差异。未做解析器层面的验证。
